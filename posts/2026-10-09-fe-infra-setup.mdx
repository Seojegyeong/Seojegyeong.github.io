whereYouAd 팀에 합류했을 때 레포가 비어있는 상태였습니다. 3인이 동시에 개발을 시작하기 전, 코드 품질 기반이 없으면 나중에 더 큰 비용이 든다는 것을 이전 프로젝트에서 경험했습니다. Sprint 1에 기능 구현 대신 인프라 구축에 시간을 먼저 썼습니다.

## 나중에 도입하면 비용이 폭발한다

린트 규칙 없이 각자 작성하다 나중에 ESLint를 추가하면, 전체 코드에 일괄 적용할 때 diff가 폭발합니다. 커밋 컨벤션이 없으면 `git log`로 히스토리를 파악하기 어렵고 PR 작성 기준도 불명확합니다. 공통 컴포넌트가 어떻게 생겼는지 보려면 코드를 직접 열어야 합니다. 이 문제들은 개발 초반에 잡는 것이 훨씬 쉽습니다.

## ESLint v9 flat config — 4파일로 관심사 분리

단일 `eslint.config.js`에 모든 규칙을 넣으면 규칙 충돌 디버깅이 어렵고 어떤 규칙이 어떤 파일에 적용되는지 파악하기 힘듭니다. 4개 파일로 분리해 각 파일의 역할을 명확히 했습니다.

```text
eslint/default.mjs     → 기본 JS 규칙 (no-console, no-unused-vars, no-floating-promises)
eslint/import.mjs      → import 정렬 순서 + 순환 의존성 감지
eslint/react.mjs       → React hooks 규칙 (exhaustive-deps 포함)
eslint/typescript.mjs  → @typescript-eslint 규칙
```

`no-floating-promises`는 처음에 오탐이 많았습니다. `void invalidateQueries(...)`처럼 백그라운드 실행 의도가 명확한 경우와 실수로 `await`를 빠뜨린 경우를 구분해야 했습니다. 팀 내에서 백그라운드 실행 의도가 있을 때만 `void`를 명시하는 기준을 정하고 ESLint가 이를 허용하도록 설정했습니다.

## GitHub Actions 3워크플로 독립 분리

단일 워크플로에 배포·검증·시각 회귀 테스트를 모두 넣으면 배포가 실패할 때 PR 검증도 함께 막힙니다. 실패 원인도 어느 단계인지 즉시 알기 어렵습니다.

```yaml
# .github/workflows/
ci.yaml       # PR → develop/main: ESLint + TypeScript build
main.yaml     # push → main: S3 업로드 → CloudFront 무효화 → Discord 알림
chromatic.yml # push → develop: Storybook 빌드 → Chromatic 시각 회귀 테스트
```

각 워크플로가 독립적으로 실행되므로 배포 워크플로 실패가 PR 검증을 막지 않습니다. 알림 채널(GitHub status check, Discord)도 역할별로 구분됩니다.

배포 워크플로 작성 중 Lighthouse CI가 `NO_FCP`로 실패한 문제를 겪었습니다. 원인은 Vite가 빌드 타임에 환경 변수를 번들에 하드코딩하는 방식이었습니다. `process.env`가 아닌 `import.meta.env`를 사용하므로 런타임 주입이 되지 않아, 빌드 단계에 secrets를 주입해야 했습니다.

## husky + lint-staged + commitlint

```bash
# .husky/pre-commit: 변경된 파일만 ESLint + Prettier 실행
npx lint-staged

# .husky/commit-msg: Conventional Commits 형식 강제
npx commitlint --edit "$1"
# feat: ..., fix: ..., docs: ..., refactor: ...
```

`lint-staged`는 변경된 파일만 처리해 전체 코드를 매번 린트하는 것보다 빠릅니다. commitlint가 있으면 `git log`를 봤을 때 각 커밋이 무엇을 하는지 바로 파악됩니다.

## Storybook + Chromatic + CodeRabbit

공통 컴포넌트 11개(Button·Input·Badge·Chart 등)를 Storybook으로 문서화했습니다. 팀원이 공통 컴포넌트를 확인하러 코드를 직접 열 필요 없이 Storybook URL을 공유하면 됩니다.

Chromatic은 develop 브랜치에 push할 때마다 Storybook 스냅샷을 비교합니다. 의도치 않은 UI 변경이 있으면 PR에서 시각적으로 경고합니다.

CodeRabbit은 PR이 열리면 자동으로 코드 리뷰 코멘트를 생성합니다. 리뷰어가 놓치기 쉬운 엣지 케이스와 잠재적 버그를 자동으로 지적해 팀 리뷰 품질을 일관되게 유지했습니다.

## 트레이드오프

Sprint 1에 인프라에 시간을 써서 기능 구현 착수가 늦어집니다. 이후 3개월간 품질 비용이 절감되어 충분히 상쇄됐지만, 마감이 촉박한 프로젝트에서는 우선순위를 다르게 설정해야 할 수 있습니다.

## 정리

인프라는 한번 만들어두면 그 이후 작업을 자동으로 지켜줍니다. 커밋마다 린트, PR마다 타입 검사, push마다 시각 회귀 테스트가 자동으로 실행됩니다. Sprint 1에 투자한 시간이 이후 3개월 동안 팀 전체의 품질 유지 비용을 낮춥니다.
