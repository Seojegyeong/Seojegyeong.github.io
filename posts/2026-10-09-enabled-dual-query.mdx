withTime 공지사항 페이지에는 두 가지 모드가 있습니다. 검색어가 없으면 전체 목록을 보여주고, 검색어가 있으면 검색 결과를 보여줍니다. 문제는 두 모드가 서로 다른 API 엔드포인트를 사용한다는 점입니다.

- 목록: `GET /notices`
- 검색: `GET /notices/search?query=검색어`

하나의 `useQuery`로 처리하려면 `queryFn` 안에서 분기해야 하는데, 같은 키를 쓰면 목록 캐시와 검색 결과 캐시가 충돌합니다. 두 쿼리를 모두 활성화하면 검색어를 입력했을 때 목록 API와 검색 API가 동시에 호출됩니다.

## enabled로 상호 배타적 전환

```ts
// useNotices.ts
function useNotices(searchQuery: string) {
  const listQueryKey = useMemo(() => ["notices", "list"], []);
  const searchQueryKey = useMemo(
    () => ["notices", "search", searchQuery],
    [searchQuery]
  );

  const listQuery = useQuery({
    queryKey: listQueryKey,
    queryFn: getNotices,
    enabled: !searchQuery,     // 검색어 없을 때만 활성화
    staleTime: 1000 * 60 * 5,
  });

  const searchResult = useQuery({
    queryKey: searchQueryKey,
    queryFn: () => searchNotices(searchQuery),
    enabled: !!searchQuery,    // 검색어 있을 때만 활성화
    staleTime: 0,              // 검색 결과는 항상 최신으로
  });

  return {
    notices: searchQuery ? searchResult.data : listQuery.data,
    isLoading: searchQuery ? searchResult.isLoading : listQuery.isLoading,
    isError: searchQuery ? searchResult.isError : listQuery.isError,
  };
}
```

`enabled: !searchQuery`와 `enabled: !!searchQuery`는 항상 반대입니다. 검색어가 있으면 목록 쿼리는 비활성화되고 검색 쿼리만 활성화됩니다.

## 상태 전환 흐름

```text
검색어 없음 (searchQuery = "")
  → listQuery:   enabled=true  → 목록 API 호출
  → searchResult: enabled=false → API 호출 없음

검색어 있음 (searchQuery = "ETF")
  → listQuery:   enabled=false → API 호출 없음 (캐시는 유지)
  → searchResult: enabled=true → 검색 API 호출
```

검색어를 지우면 목록 쿼리가 다시 활성화됩니다. 목록 데이터는 캐시에 남아있으므로 `staleTime` 이내라면 재요청 없이 즉시 표시됩니다. 검색 → 목록 전환이 빠릅니다.

## useMemo로 쿼리 키 안정화

`["notices", "list"]`처럼 배열 리터럴을 직접 쓰면 렌더마다 새 배열 인스턴스가 생성됩니다. JavaScript에서 `[] !== []`이므로 참조가 매번 다릅니다.

TanStack Query v5는 내부적으로 직렬화 비교를 하므로 실제로 문제가 생기지 않는 경우가 많습니다. 그러나 `useMemo`로 안정화하면 의도를 명확히 표현합니다. deps가 변경되지 않는 한 같은 참조를 유지한다는 것을 코드에서 바로 읽을 수 있습니다.

```ts
// deps가 없으면 마운트 시 한 번만 생성
const listQueryKey = useMemo(() => ["notices", "list"], []);

// searchQuery가 바뀔 때만 새 배열 생성
const searchQueryKey = useMemo(
  () => ["notices", "search", searchQuery],
  [searchQuery]
);
```

## 쿼리 키 분리 이유

목록과 검색이 같은 쿼리 키를 공유하면 목록 캐시가 검색 결과로 오염되거나, 검색 캐시가 목록 자리에 표시됩니다. 키를 분리하면 각각 독립적인 캐시를 가집니다. `["notices", "list"]`와 `["notices", "search", searchQuery]`는 서로 다른 캐시 엔트리입니다.

쿼리 키를 잘 설계하면 `enabled` 전환 시 원하지 않는 캐시 재사용도 방지할 수 있습니다. 검색 쿼리 키에 `searchQuery`를 포함시켰으므로 "ETF" 검색과 "채권" 검색은 서로 다른 캐시를 가집니다. 이전 검색 결과는 별도로 캐싱되어 같은 검색어를 다시 입력하면 빠르게 응답합니다.
