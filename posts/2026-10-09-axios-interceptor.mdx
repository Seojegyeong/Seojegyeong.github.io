Roome 개발 초반에 일부 API에서 성공 응답인데도 에러로 처리되는 버그가 있었습니다. 원인을 찾고 보니 서버가 성공 여부를 나타내는 키를 `success`와 `isSuccess` 두 가지로 반환하고 있었습니다. 서버 개발 초기에 `isSuccess`로 시작했다가 중간에 `success`로 변경했는데, 두 버전이 혼재된 상태로 배포된 것이었습니다.

## 세 가지 공통 처리를 인터셉터에 집중

API 호출 코드에서 매번 처리하던 세 가지를 인터셉터로 옮겼습니다.

**문제 1 — success/isSuccess 혼재**

클라이언트가 `success`만 체크하면 `isSuccess`를 반환하는 API에서 성공이 에러로 처리됩니다. 반대도 마찬가지입니다. API마다 어느 키를 쓰는지 확인하며 개발하는 것은 너무 번거롭습니다.

**문제 2 — FormData Content-Type**

이미지 업로드 시 `Content-Type: multipart/form-data; boundary=...`가 필요합니다. `boundary` 파라미터는 axios가 FormData를 감지해 자동으로 생성합니다. 개발자가 수동으로 `Content-Type: multipart/form-data`를 설정하면 boundary가 없어 서버가 파싱하지 못합니다.

**문제 3 — 인증 불필요 API에 토큰 주입**

로그인·회원가입 API에도 Authorization 헤더가 붙으면 서버 오류가 발생했습니다. API마다 토큰 첨부 여부를 수동으로 제어하는 것은 누락 위험이 있습니다.

## 인터셉터 구현

```ts
// src/lib/apiClient.ts

const apiClient = axios.create({
  baseURL: import.meta.env.VITE_API_BASE_URL,
  timeout: 10000,
});

const AUTH_FREE_PATHS = [
  "/auth/login",
  "/auth/signup",
  "/auth/reissue",
  "/products/public",
] as const;

// 요청 인터셉터
apiClient.interceptors.request.use((config) => {
  const token = getToken();

  const isAuthFree = AUTH_FREE_PATHS.some((path) => config.url?.includes(path));
  if (token && !isAuthFree) {
    config.headers.Authorization = `Bearer ${token}`;
  }

  // FormData 자동 감지 → Content-Type 삭제 (axios가 boundary 포함 자동 설정)
  if (config.data instanceof FormData) {
    delete config.headers["Content-Type"];
  }

  return config;
});

// 응답 인터셉터
apiClient.interceptors.response.use(
  (response) => {
    const data = response.data;
    // success와 isSuccess 양쪽 처리
    const isSuccess = data?.success ?? data?.isSuccess;

    if (isSuccess === false) {
      return Promise.reject(new Error(data?.message ?? "요청 실패"));
    }
    return response;
  },
  (error) => Promise.reject(error.response?.data ?? error)
);
```

## FormData Content-Type을 삭제하는 이유

`multipart/form-data` 요청은 각 파트를 구분하는 `boundary`가 헤더에 포함되어야 합니다.

```http
Content-Type: multipart/form-data; boundary=----WebKitFormBoundary7MA4YWx
```

axios는 `config.data`가 `FormData` 인스턴스임을 감지하면 이 헤더를 자동으로 생성합니다. 그런데 요청 인터셉터나 기본 헤더에 `Content-Type: multipart/form-data`를 수동으로 설정해 두면, axios는 이미 헤더가 있다고 판단해 boundary를 추가하지 않습니다. boundary 없는 multipart 요청은 서버가 파싱하지 못합니다. 헤더를 삭제하면 axios가 올바른 헤더를 자동으로 생성합니다.

## success ?? isSuccess 처리의 의미

`??` (nullish coalescing)을 사용하면 `data?.success`가 `null`이나 `undefined`일 때만 `data?.isSuccess`를 확인합니다. `success`가 있는 API는 해당 값을 쓰고, `success`가 없는 API는 `isSuccess`를 씁니다.

`isSuccess === false` 조건으로 에러를 처리합니다. `null`이나 `undefined`인 경우는 에러로 처리하지 않아, 성공 키가 없는 응답(예: 단순 데이터 반환)을 에러로 잘못 처리하는 것을 방지합니다.

## 트레이드오프

서버 응답 구조가 정규화된 이후에도 `success ?? isSuccess` 처리가 남아있으면 기술 부채가 됩니다. 서버와 협의해 단일 키로 통일되면 인터셉터를 단순화해야 합니다.

AUTH_FREE_PATHS는 URL 문자열 매칭 방식입니다. 경로가 변경되면 리스트도 함께 업데이트해야 합니다.

## 정리

인터셉터에서 공통 처리를 집중하면 API 함수를 작성할 때 토큰 처리, FormData 처리, 응답 성공 여부 확인을 신경 쓰지 않아도 됩니다. 팀 개발에서는 각자가 같은 처리를 반복 구현하거나 누락하는 실수를 방지하는 효과가 있습니다.
