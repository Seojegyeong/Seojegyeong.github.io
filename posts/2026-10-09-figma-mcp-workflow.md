light를 1인으로 개발하면서 기획→디자인→구현 흐름이 매번 병목이었습니다. 기획 문서를 작성하면 그것을 보고 Figma에서 직접 디자인해야 합니다. Figma 작업이 끝나면 디자인을 보면서 코드를 구현합니다. 디자인을 수정하면 코드도 다시 수정합니다. 각 단계가 독립된 도구에서 이루어지니 컨텍스트를 계속 다시 설명해야 했습니다.

## 도구가 분리될 때 생기는 컨텍스트 전환 비용

1인 프로젝트에서 기획자·디자이너·개발자를 혼자 맡으면 각 역할 전환마다 비용이 생깁니다.

```text
기획 문서 작성 (마크다운)
  → Figma 열기 → 기획서 다시 읽기 → 수동으로 레이아웃 구성
  → VS Code 열기 → Figma 보면서 컴포넌트 수동 구현
  → 디자인 수정 필요 → Figma 다시 열기 → 코드도 다시 수정
```

Figma 조작 자체도 시간이 걸립니다. 디자인 도구 전문성이 없으면 원하는 레이아웃을 만드는 데만 시간을 많이 씁니다.

## Figma MCP + Claude Code 통합 워크플로

Claude Code에 Figma MCP를 연결하면 Claude가 Figma 파일을 직접 읽고 쓸 수 있습니다. 기획 문서를 프롬프트로 전달하면 Claude가 Figma에 레이아웃·컴포넌트를 자동으로 배치합니다. 자연어로 피드백을 주면 Figma 내 요소가 수정됩니다.

```text
기획 문서 (마크다운)
  → Claude Code에 Figma MCP 연결
  → "이 기획 기반으로 Light 확장 프로그램 팝업 UI 생성해줘"
  → Figma에 디자인 초안 자동 생성
  → "용어 카드 여백 더 좁게, 토글 스위치 오른쪽 정렬"
  → Figma 자동 수정
  → "이 Figma 컴포넌트를 React + Tailwind로 구현해줘"
  → 디자인 기반 React 컴포넌트 생성
```

단일 세션 안에서 기획→디자인→구현이 연결됩니다. 도구를 전환할 때마다 "지금까지 한 것"을 다시 설명하는 비용이 사라집니다.

## 단일 컨텍스트의 실제 의미

기획 문서를 Claude에게 한 번 전달하면 Claude는 그 내용을 유지한 채로 Figma 작업과 코드 생성을 이어서 합니다. 디자인 피드백("버튼을 왼쪽으로")이 코드 수정("`justify-content: flex-start`")과 같은 세션 안에서 연결됩니다.

이 방식이 실질적으로 달라지는 것은 **재설명 비용의 제거**입니다. Figma를 직접 열어 작업할 때는 기획서를 보면서 직접 프레임을 만들고 컴포넌트를 배치해야 합니다. 코드로 넘어올 때는 Figma를 다시 열어 치수를 확인합니다. Claude Code 세션 하나에서는 이 확인 과정이 자동으로 이루어집니다.

## 트레이드오프

AI가 생성한 디자인이 의도와 다를 때 수정 프롬프트가 필요합니다. AI가 기획 의도를 완벽히 파악하지 못하는 경우 반복 조정이 생깁니다. 세밀한 디자인 제어(애니메이션 타이밍, 복잡한 인터랙션)는 수동 조정이 더 효율적이었습니다.

Figma MCP 초기 설정에 시간이 필요합니다. 연결 후에는 워크플로가 빠르게 돌아가지만, MCP 서버 설정과 Figma API 연동을 처음 구성할 때는 문서를 꼼꼼히 읽어야 했습니다.

## 정리

1인 프로젝트에서 기획·디자인·구현을 혼자 맡으면 각 단계의 도구 전환이 생산성을 낮춥니다. Figma MCP와 Claude Code를 연결하면 세 단계가 하나의 흐름으로 이어집니다. light 프로젝트에서 이 워크플로를 경험한 이후, 새 프로젝트를 시작할 때 AI 도구 통합을 워크플로 설계의 첫 단계로 고려하게 됐습니다.
